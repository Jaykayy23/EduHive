# Authentication deployment and cutover

EduHive uses pinned stable Better Auth 1.7.14 with its Prisma adapter for database-backed, signed-cookie sessions. Public username login, signup, Google initiation/callback, verification and recovery URLs remain unchanged. Existing server actions keep the database-backed abuse limits; Google token exchange stays with Arctic. Native Better Auth HTTP endpoints are deliberately not mounted: adding a catch-all later requires equivalent rate limits, account provisioning and verification policy first.

The compatibility check on 2026-10-29 used package metadata and Node 22.14, Next.js 16, React 18.3 and Prisma 5.22. The frontend was subsequently patched to Next.js 16.4.3. The auth release declares Next 14–16, React 18–19 and Prisma 5–7 support. See [installation](https://better-auth.com/docs/installation), [Prisma adapter](https://better-auth.com/docs/adapters/prisma) and [session management](https://better-auth.com/docs/concepts/session-management). No beta dependency was selected.

## Configuration

Set server-only `BETTER_AUTH_URL` to the exact application origin and `BETTER_AUTH_SECRET` to a cryptographically random secret of at least 32 characters. Generate one with `node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"`. Never put the secret in a `NEXT_PUBLIC_` variable or source control.

Optional `AUTH_TRUSTED_ORIGINS` is a comma-separated list of exact additional origins. Paths, query strings, credentials and non-HTTP protocols are rejected; production requires HTTPS. Google OAuth accepts only a configured origin and retains `/api/auth/callback/google`; register that exact URI for each allowed host with Google. Keep `APP_URL` (email links) consistent with the canonical origin. Additional hosts also need correct Next.js Server Action origin/proxy configuration if applicable; do not allow arbitrary forwarded hosts.

Existing Google, Resend, database and email variables remain required for their respective workflows. No public native Better Auth endpoint is needed. Password login remains case-insensitive by username and verifies the original Argon2 hash without replacing it. The application shared `validateRequest()` returns only the established public user/session shape, never hashes, email recovery tokens or session bearer tokens.

## Reviewed operator cutover

1. Stop authentication writes or put the deployment in maintenance mode. Take and restore-test a complete encrypted database backup; record the previous application artifact and provider configuration. Keep the backup outside the source distribution.
2. Rehearse on a private restored staging database, never a live student-data fixture. Review `prisma/migrations/20261029000000_add_better_auth/migration.sql`. It adds tables/columns and backfills the verification boolean from the existing timestamp, preserving user IDs, usernames, Argon2 hashes, Google subjects and all content relationships.
3. Set the intended database explicitly in the operator shell, then run `npx prisma migrate deploy` and `npx prisma generate`. These commands are manual deployment steps, not automatically run by this change. Existing installations must already have the baseline migration resolved correctly; follow the setup guide before migration deployment.
4. Set `AUTH_MIGRATION_DATABASE_URL` explicitly to that same intended database. The account migration deliberately ignores `DATABASE_URL` to prevent accidental targeting. Run `node scripts/migrate-auth.mjs --dry-run`, review counts, then `node scripts/migrate-auth.mjs --apply`. Dry-run writes nothing; apply runs in one transaction and repeated application creates no duplicate credentials/Google accounts. An identity owned by another application user stops migration. Output contains counts only. Avoid shell history containing real database passwords.
5. Configure the auth secret/origins and deploy the new application. Require everyone to sign in again. Test legacy password login, wrong passwords, Google identity matching, verification/resend, recovery, onboarding and protected content ownership on the intended deployment before ending maintenance mode.

Account rows copy the existing password hashes and Google subjects without changing the authoritative application user record. New signup, Google linking and password recovery keep account records synchronized. Existing verification/reset token tables and hashed tokens remain accepted for their original bounded lifetime; existing resend and forgot-password pages remain the recovery path after expiry. There is no forced password reset solely for migration.

## Session policy and rollback

New sessions live in `auth_sessions`, expire after 30 days and renew after one day of use. Cookies are signed, HTTP-only, SameSite=Lax and secure in production. Validation always reads database state; cookie caching is disabled. Writable server contexts refresh/clear cookies, while Server Components tolerate immutable cookie stores. Expired/revoked sessions fail closed. Unverified accounts cannot create sessions and lose any existing session at validation. Logout deletes the server session. Password reset atomically consumes its one-time token, updates both password representations, verifies the email and deletes both old and new sessions; replay cannot reset again.

Legacy Lucia sessions remain in the old table for controlled rollback but are never accepted by the new application. Do not revive them by casually rolling back code. If rollback is necessary, stop writes, revoke all sessions in both tables, restore the previous application/configuration and verify legacy recovery behavior. Prefer a forward fix after new accounts/password changes occur. Restoring a pre-cutover backup discards later writes and requires a separately approved recovery decision. Retain additive tables until the rollback window closes; this task does not drop them or execute production migration/reset commands. Changing the signing secret forces re-login.

## Reproducible verification

`npm test` runs credential-free policy, Argon2, migration and real Better Auth memory-adapter lifecycle tests. `npm run test:auth:db` is a separate integration test and fails when its database is not explicitly provided. It requires `psql` on PATH (or `PG_BIN` pointing to its bin directory), an **empty** disposable PostgreSQL database, and `AUTH_TEST_DATABASE_URL` on localhost/127.0.0.1 with a database name starting `eduhive_auth_test`. It refuses an existing public schema and never drops/reset tables. Create a fresh database per run; do not run Prisma deploy first because the test exercises old migrations and seeded legacy records before applying the additive migration.

For example, against an independently started loopback fixture PostgreSQL: create `eduhive_auth_test_001` using `createdb`; set `AUTH_TEST_DATABASE_URL=postgresql://fixture_user@127.0.0.1:55439/eduhive_auth_test_001` in the shell; then run `npm run test:auth:db`. Use only disposable local fixture credentials. Windows can set `PG_BIN=C:/Program Files/PostgreSQL/18/bin`. Stop the fixture server after testing. Never point these tests at `.env` or production.

On 2026-10-29, the database integration passed against a new local PostgreSQL 18.6 cluster on loopback port 55439. It applied the old schema, seeded a fixture user/post/reset token, applied the additive migration, proved unchanged user IDs/hash/Google identity/content/token, proved migration dry-run/idempotency, then exercised the actual Prisma session lifecycle and shared recovery transaction. This is local fixture evidence. Real Google consent, Resend delivery/DNS, browser cookies across the production proxy and live signup/recovery still require deployment verification with the buyer accounts.
